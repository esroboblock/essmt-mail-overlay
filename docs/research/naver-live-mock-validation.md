# 실제 네이버 메일 MV3 Mock 삽입 검증

검증일: 2026-11-06 KST. 대상 구현: 커밋 `e11d034`의 확장(확장 런타임 코드는 `7083109`와 동일).

**실제 로그인된 네이버 받은메일함에서 설치된 MV3 확장이 합성 Mock 태그를 삽입하는 데 성공했다.** 실제 ESSMT 태그/API 연결을 검증한 것은 아니다. [선행 합성·읽기 전용 조사](naver-compatibility-validation.md) 이후 사용자가 기존 세션 사용을 추가 허용한 범위에서 진행했다.

## 사용 환경과 권한 범위

- es2003의 기존 로그인 프로필, Chrome 151.0.7922.77 / CDP 1.3, headless의 실제 `https://mail.naver.com` 받은메일함. 로컬 합성 응답으로 사이트를 대체하지 않았다.
- 사용자가 이번 작업에 한해 분리된 프로필 조건을 철회하고 사용 가능한 기존 세션을 허용했다. 이는 일반 배포/설치 지침을 변경한 것이 아니다. 프로필·세션·쿠키·토큰을 복제하거나 추출하지 않았다.
- 수집 확장만 허용하는 기존 시작 옵션에서는 `Extensions.loadUnpacked`가 ID를 반환하더라도 실험 확장이 실제로 등록되지 않았다. 동일 Chrome의 **비로그인 임시 프로필**에서 허용 목록 유무/두 확장 시작 로드를 비교해 이 현상을 재현했다. 설치 명령의 성공 응답만으로 실제 설치 성공을 판정하지 않았다.
- 원래 서비스/스크립트/수집 확장 파일을 수정하지 않고, 브라우저 서비스를 한시적으로 멈춘 뒤 **같은 프로필·실행 파일·기존 인수**의 두 확장 옵션에 실험 확장만 추가한 임시 Chrome을 실행했다. 기존 수집 확장도 함께 활성화했다.
- 임시 실행은 8분 제한의 transient systemd unit에서 수행했다. 원래 PID 종료와 포트 해제를 확인한 뒤 프로필을 열었고, 프로필 잠금을 삭제하지 않았다. own PID·고유 WebSocket으로 임시 Chrome만 닫으며, 연결 단절/시간 초과에도 임시 자식 프로세스를 종료한 후 원래 서비스를 시작하는 복구 절차를 먼저 마련했다.
- 시험 탭과 팝업만 조작·정리했다. 메일 삭제/이동/발송, 읽음·중요 상태의 직접 토글, ESSMT 운영 API/DB 호출이나 수집 설정·커서 조작은 하지 않았다. 원래 브라우저 서비스의 일시 중단·복구는 있었으며 파이프라인 무중단을 주장하지 않는다.

브라우저 레지스트리에서 실험 확장 1개와 기존 수집 확장 1개가 모두 활성화된 것을 확인한 뒤, 같은 로그인 프로필의 시험 탭을 열었다. 배지 생성은 **MV3 content script**가 수행했다. 시험 도구는 결과 집계·UI 조작만 수행했으며 렌더러를 페이지 평가로 대신 실행하지 않았다.

## 레이아웃: 충돌 검사와 가시성의 구분

첫 실제 실행의 800px·360px·1280px viewport와 스크롤 후 상태에서, 현재 배지 27개의 제목 영역 내 수직 잘림 및 첨부/preview/popup 사각형과의 겹침은 각각 0건이었다. 배지 높이는 약 20.80px이고 태그 행 높이는 모두 39px로 유지됐다. 최소 배지 폭은 800/360px에서 약 30.55px, 1280px에서 약 71.92px였다. 긴 태그는 확장 CSS의 말줄임과 title 속성으로 처리한다.

**이 검사만으로 좁은 화면에서 배지가 실제로 보인다고 판정하지 않는다.** 확장 제거·원래 서비스 복구 후 별도 시험 탭에서 원본 화면을 비교했다. 원본도 800px와 360px에서 목록 폭 773px·행 폭 708px·제목 폭 236px를 유지했고, 첫 제목 영역의 x좌표는 570~806px였다. 따라서 360px viewport에서는 원본 제목 영역 자체가 화면 밖이다. 1280px에서는 원본 제목 폭이 492px였다. 이 한 계정의 데스크톱 UI 측정으로 모바일/다른 보기 모드의 호환성을 주장하지 않는다.

첫 실행의 크기 검사는 DOM 배치/겹침 검사이며, viewport 및 조상 overflow에 의한 가로 잘림은 별도로 확인해야 한다. 후속 검사에서는 800px·1280px 모두 배지 27개가 제목/viewport/overflow 조상의 가로 범위 안에 있었고, 360px에서는 27개 모두 가로 화면 밖이었다. 화면에 세로로 들어온 태그 행에서도 360px 배지의 실제 가시 폭은 0px였다. 따라서 360px 데스크톱 화면을 지원한다고 판정하지 않는다.

## 개인정보·원래 환경 복구

- 실제 href/class/SN은 브라우저 또는 원격 시험 프로세스 메모리에서만 비교했다. 결과는 건수·boolean·일반 CSS/기하 수치뿐이다. 실제 메일 제목/본문/주소/운영 SN/쿠키/토큰/원본 HTML/스크린샷/HAR/네트워크 body를 공개 파일·댓글·외부 Mock 서버에 남기지 않았다.
- Naver Mock 조회는 격리 world 안의 메모리 연산이며 postMessage/스토리지/조회 서버를 사용하지 않는다. 테스트 매핑도 저장하지 않았다.
- 첫 시험 후 원래 Chrome 서비스 `active`, 새로 열린 인증된 받은메일함 80행, 기존 수집 확장 1개 활성화, 실험 확장·배지 0개를 독립적으로 재확인했다. 전체 인입 파이프라인의 DB/health를 검증한 것은 아니다.

## 남는 한계

읽음·중요 토글, 키보드·확대/축소·접근성, 메일 이동/복사·계정 전환, 실제로 식별 불가/중복 SN이 나타나는 화면은 별도 검증이 필요하다. 실제 화면에서 노드를 인위적으로 다른 운영 SN으로 바꾸지 않았다. 행 재사용·오래된 응답의 일반 회귀는 기존 합성 E2E와 실제 관찰 범위를 구분한다. 운영 API/인증/DB·스토어 배포는 이번 작업에 포함되지 않는다.


## 후속 실제 SPA·검색·가시성 검증

기본 250ms 조건의 최종 종합 실행은 9개 받은메일함 스냅샷에서 정확성 오류 0, 배치/충돌 오류 0, 1280px 가로 가시성 오류 0을 확인했다. 360px 가로 가시성 제한 1개 조건은 성공과 분리해 기록했다.

| 실제 조작/관찰 | 결과와 해석 |
| --- | --- |
| 전체메일 전환 | 실제 전체메일 경로 진입을 boolean으로 확인, 목록 80행, 배지 0개 |
| 보낸메일 전환 | 실제 보낸메일 경로 진입 확인, 목록 80행, 배지 0개 |
| 위 화면에서 뒤로가기 | 받은메일함 80/80 결과와 배지 27개 복구 |
| 검색 | 고정 합성 검색어만 입력·Enter. URL 변경 후 목록/배지 0개, 뒤로가기 후 80/80 복구 |
| 검색 화면 식별 보완 | 도구의 최초 `/v2/search` 가정은 맞지 않았다. 복구된 원본 환경에서 같은 합성 검색을 추가 관찰해 `/v2/folders/{number}/search` 형태, URL의 합성 검색어 포함과 문서 제목의 검색 표시를 확인했다. 실제 folder 값·query 원문은 출력하지 않았다. 빈 검색 전환을 확인한 것이며 **메일이 있는 검색 결과의 식별/태그 지원은 미검증** |
| 실제 노드 수명 | 전체/보낸/검색에서 돌아올 때 목록 root 교체, 재사용된 행 노드 0개, 재사용 노드의 식별 변경 0개. 실제 같은 노드의 다른 mailSN 재바인딩을 증명하지 않는다 |
| 지연 중 전환 시도 | 받은메일함 복귀 시 loading을 관찰했지만 전환 클릭 직전에는 이미 종료되어 **기본 250ms 조건의 경쟁 상황을 포착하지 못함**. 별도 2초 지연 변형은 아래에서 확인했다. 전환 400ms 후 미지원 화면 배지 0, 복귀 후 80/80은 확인 |
| 상세 | `read` 클래스와 read input checked가 모두 있는 행만 클릭. 같은 탭의 상세 경로로 이동, 배지 0개. 팝업 버튼 자체는 누르지 않음 |

전체메일·보낸메일·검색·상세에 태그를 표시하는 기능을 구현한 것은 아니다. 현재 지원 밖 화면에서 배지를 제거하고, 지원하는 받은메일함으로 돌아오면 다시 매핑하는 동작의 검증이다. 다른 화면의 DOM에서 SN을 새로 추출해 업무 태그를 붙인 성공으로 해석하면 안 된다.

실제 화면의 식별 불가·중복 SN은 이번 80행에 없었다. 이러한 처리 및 같은 행의 A→B→A 재바인딩·늦은 응답은 기존 합성 테스트 결과를 유지한다. 합성 결과를 실제 race 검증으로 대체하지 않으며, 아래 실제 지연 주입 결과도 관찰한 전환 한 경우로 한정한다.

## 2초 Mock 지연을 주입한 실제 전환 시험

기본 250ms 조건에서는 클릭 직전까지 loading을 유지하지 못했으므로, 저장소/배포 소스를 바꾸지 않고 **임시 시험 묶음의 Mock 기본 대기 값만 2000ms**로 바꿔 별도 MV3 실행을 했다. 기존 수집 확장 존재·활성화와 원래 경로를 확인한 뒤 같은 복구 감시 절차를 사용했다. 운영 API 지연이나 모든 race를 재현했다는 뜻은 아니다.

- 처음 받은메일함: 80행/80개 결과 일치, 배지 27개.
- 실제 전체메일 → 브라우저 뒤로가기로 받은메일함 복귀 후, **80행 loading 상태가 있는 것을 전환 클릭 직전에 확인**했다.
- 실제 보낸메일함으로 전환하고 2300ms(2초 Mock 대기보다 길게) 기다린 뒤, 보낸메일 경로에서 **배지 0개·확장 행 상태 0개**를 확인했다.
- 받은메일함으로 다시 돌아와 **80/80 일치·배지 27개**를 확인했다.

이는 실제 SPA 화면의 응답 대기 중 이탈·취소/수명 무효화와 복귀 동작을 확인한 사례다. 동일 DOM 노드에 다른 운영 SN을 넣는 조작이나 중단을 무시하는 실제 ESSMT 서버 응답은 시험하지 않았다. 저장소의 기본 Mock 대기는 계속 250ms다.

## 실행·복구 및 자동 회귀 결과

한시적 실제 실행을 네 번 수행했다. 첫 실행은 삽입·선택/스크롤·기하·상세 시험을 통과했다. 두 번째는 전체/보낸 전환까지 확인한 뒤 시험 도구의 검색 키 입력 오류로 중단됐고, 자동 복구를 확인했다. 설치된 Puppeteer는 `Control+A`를 단일 키 이름으로 받지 않으므로 Control down/KeyA/up으로 고친 뒤 세 번째 실행을 마쳤다. 네 번째 실행에서는 별도의 2초 지연 변형만 시험했다. 이 오류는 확장 소스의 실패가 아니며 중단된 실행을 전체 성공으로 집계하지 않았다. 각 실행의 unit wall time은 약 22초·26초·38초·26초였으며 원래 서비스 복구 절차를 포함한다.

각 복구를 확인했고 마지막 2초 변형 이후에도 독립 CDP/서비스 조회에서 다음을 확인했다.

- 원래 Chrome 서비스 active, 기존 인증된 받은메일함 탭 1개·80행.
- 원래 경로의 수집 확장 1개 활성화, 실험 확장 0개.
- 확장 root/배지 표식 0개. 임시 브라우저/시험 탭/팝업 종료.
- 별도 원본 검색 확인용 탭도 종료. 세션 재로그인은 필요하지 않았다.

로컬 자동 회귀는 `npm test` **25/25**, `npm run test:e2e` **38/38**(23.5초) 통과했다. 이는 기존 데모·합성 Naver의 자동 테스트이며 위 실제 세션 assertion과 구분한다. 새로운 소스 변경이 필요한 호환성 결함은 이번 범위에서 관찰하지 않아 확장 런타임 코드는 변경하지 않았다. 실제 서버 조사로 검증 범위·설치 조건·모바일 한계를 문서화했다.

운영 API 전에는 실제 계정 namespace·인증/권한, SN NULL/중복/폴더별 업무 태그 차이의 해소 정책, 배치/오류 계약·캐시 무효화가 필요하다. 현재 합성 규칙의 성공은 ESSMT DB 매칭 성공이 아니다.
