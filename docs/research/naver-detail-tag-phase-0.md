# 네이버 상세 메일의 ESSMT 태그 편집 기술 검증

2026-11-13 KST · [Overlay #13](https://github.com/esroboblock/essmt-mail-overlay/issues/13) Phase 0. 검토 기준은 Overlay main `6aff746` 및 ESSMT main `6e4bb164`이다.

상세 화면의 태그 UI와 ESSMT 태그 편집은 구현 가능한 구조다. 실제 네이버 상세에서 **현재 렌더링된 메시지의 SN과 계정·데이터셋 일치를 확인할 근거**는 아직 확보하지 못했다. Phase 1 계약 검토는 진행할 수 있다. Phase 1 구현 착수와 Phase 2 실환경 활성화는 각각 아래의 식별·보안 조건을 충족한 뒤 판단한다.

## 실제 화면에서 확보한 근거

| 근거 | 확인 범위 |
| --- | --- |
| [받은메일함 DOM 조사](naver-webmail-dom.md) | 제목 링크의 상대 경로 `/v2/popup/read/{folderSN}/{mailSN}`과 행의 `mail-{mailSN}`이 80/80 일치했다. 링크 형식은 목록의 메시지 식별 근거다. |
| [실제 Naver Mock 검증](naver-live-mock-validation.md) | 이미 읽은 받은메일함 행의 제목을 클릭하자 같은 탭에서 상세 경로로 이동하고 목록 배지가 제거됐다. 실제 상세 URL 형태, frame 구성 및 문서 ID는 기록되지 않았다. 팝업 버튼은 시험하지 않았다. |
| [Overlay PR #10](https://github.com/esroboblock/essmt-mail-overlay/pull/10) 및 [#11 검증 댓글](https://github.com/esroboblock/essmt-mail-overlay/issues/11#issuecomment-6846721430) | 전체메일도 목록 식별과 운영 태그 표시가 확인됐다. 전체메일에서 상세를 열 때의 전환은 미확인이다. |
| ESSMT의 기존 원문 링크 생성 | `/v2/read/{folderSN}/{mailSN}`을 만든다. 브라우저에서 제목을 클릭했을 때 이 경로로 열리는지, popup href와 SN이 대응하는지는 미확인이다. |

이번에는 저장소와 선행 실환경 기록을 읽었다. 실제 메일을 새로 열거나 운영 데이터를 변경하지 않았다. 동일 탭 내 SPA 여부, 상세 DOM 교체 시점, 별도 팝업·iframe, 이전/다음·닫기·새로고침에서의 URL과 메시지 전환은 새 실험이 필요하다.

## 상세 메시지 식별

- **URL**은 우선 조사할 후보다. 실제 클릭으로 확인한 origin과 정확한 상세 route만 허용하고, SN은 현재 서버 계약과 같은 양의 int32 범위의 정규 십진 문자열로 처리한다. 현재 URL과 렌더링이 비동기적으로 어긋날 수 있으므로 URL 단독 근거로 쓰기를 허용하지 않는다.
- **상세 DOM**에서는 현재 표시 중인 단일 메일에 연결된 의미 있는 SN 속성이나 공식 동작 링크가 있는지 확인한다. 재사용 루트 안에 이전 SN이 남거나, 대화 보기에서 여러 메일을 구별할 수 없으면 조회와 편집을 중지한다. 구체적인 선택자는 아직 없다.
- **목록 컨텍스트**는 첫 진입의 교차 검증 후보이다. 검증된 제목 href와 행 클래스에서 얻은 예상 SN을 같은 탭의 짧은 전환 수명에만 사용한다. 직접 진입·새 문서·팝업·다음/이전의 현재 메시지 증거를 대체할 수 없다.
- 제목·발신자·시각·thread ID·Message-ID·folderSN은 대체 키로 사용하지 않는다. 렌더링 준비, 식별 근거의 일치와 문서 상태가 모두 확인되기까지 패널을 비운다. 불일치, 중복, 이탈 또는 A→B→A 전환 시 새 화면 세대로 처리한다.

## UI 후보와 합성 시험

상세 제목·메타데이터 헤더 뒤, 본문과 기본 동작 툴바 바깥의 같은 문서에 확장 소유 섹션을 형제로 삽입하는 안을 우선한다. 실제 후보 노드가 확인되지 않으면 삽입을 보류한다. 칩과 이름이 명확한 해제 버튼, 검색 입력, 최근 사용 태그, 기존 태그 선택과 별도의 새 태그 생성·부착 버튼을 둔다. 본문이나 네이버 링크를 감싸지 않고, 페이지 단축키를 가로채는 전역 핸들러도 두지 않는다. 입력·결과·오류를 접근 가능한 이름과 상태 영역으로 표시한다. 권한 없음·미매칭·모호함은 편집 비활성으로 표시한다.

임시 Playwright Chromium 합성 DOM PoC에서 360px viewport의 헤더와 본문 사이 삽입, 기존 다음 버튼 동작, 검색 입력·추가 버튼·본문 링크의 순차 키보드 탐색, 헤더 교체 후 패널 한 개 유지까지 확인했다. 교체 시 시험 핸들러가 명시적으로 다시 삽입했다. 실제 네이버 선택자, 자동 재마운트 타이밍, 좁은 화면의 실제 가시성 또는 MV3 상세 쓰기는 이 PoC 범위 밖이다. PoC에는 외부 네트워크 요청이나 서버 쓰기가 없다.

## 계정·문서 및 쓰기 경계

현재 Worker의 확인은 탭 ID와 최상위 문서 ID를 묶는다. 지원 목록에서만 확인과 조회가 가능하다. `#gnb_name1` 감시는 DOM에서 표시 이름의 변화·소실·요소 교체를 감지하는 보조 장치다. 동일 이름으로 바뀌거나 헤더 갱신이 늦을 수 있다. DOM은 네이버 페이지가 통제하며 ESSMT 직원 세션은 네이버 계정의 증명이 아니다.

- 최초 지원 후보는 검증된 동일 탭의 단일 메시지 상세다. 기존 목록 확인을 자동 승계해 쓰기를 승인하지 않는다. 상세 쓰기에 사용할 신뢰 가능한 계정·데이터셋 바인딩을 별도로 결정한다. 확보 전에는 실제 상세 쓰기를 활성화하지 않는다.
- 새 창·팝업·직접 진입·새로고침은 별도 문서로 간주한다. opener나 이전 탭의 확인을 복사하지 않는다. 지원을 추가하면 각 최상위 문서를 독립적으로 검증한다. 여러 상세 탭은 활성 탭 추정 없이 발신 탭과 문서에 묶는다. iframe은 최초 범위에서 제외한다.
- Worker는 확장 ID, 발신 탭·최상위 frame·문서 ID·활성 문서와 허용 상세 URL, 현재 계정 바인딩, 요청 당시의 메시지 ID/화면 세대를 확인한다. URL에 신뢰 가능한 SN이 확인되면 Worker가 URL에서 독립적으로 대조한다. 변경은 확장 소유 UI의 명시적 사용자 동작으로만 만들고, 페이지 메시지로 수정 명령을 받지 않는다.
- 다음/이전, 루트 교체, 문서 이탈·종료, 계정 전환·로그아웃 때 UI를 잠그고 진행 중 결과를 버린다. 전송 직전 재확인하고 아직 보내지 않은 작업을 취소한다. 이미 서버에 도달한 요청은 탭 전환이나 네트워크 취소로 되돌릴 수 없으므로 서버에서 승인한 원래 대상에만 적용한다. 타임아웃 후 동일 동작을 자동 재전송하기 전에 현재 대상의 태그를 다시 조회한다.
- ESSMT는 매 요청 직원 세션·계정 상태·별도 쓰기 grant·서버 namespace를 재검증한다. 401/403이면 현재 편집 상태와 배지를 비우고 다시 로그인 또는 권한 확인을 안내한다.

## Phase 1 최소 API 초안

아래 경로는 제안이다. 확장 전용 JSON API로 분리하고 내부 메일 PK와 메일 내용은 응답에 포함하지 않는다.

| 동작 | 요청 및 결과 |
| --- | --- |
| 현재 태그 | 기존 `POST /api/browser-overlay/email-tags/lookup`에 메시지 한 건. `matched`와 빈 태그, `unmatched`, `ambiguous` 의미 유지. |
| 검색·최근 사용 | `POST /api/browser-overlay/email-tags/suggestions`. `namespace`, `mail_sn`, 선택적 `query`. 빈 검색어는 데이터셋 공용 최근 부착 순. 현재 메일에 붙은 태그를 제외한 제한된 `{id,name}` 목록. |
| 기존 태그 부착 또는 생성·부착 | `POST /api/browser-overlay/email-tags/attach`. `namespace`, `mail_sn`, `tag_id` 또는 `name` 중 하나. 서버 정규화 후 기존 정의 재사용. |
| 부착 해제 | `POST /api/browser-overlay/email-tags/detach`. `namespace`, `mail_sn`, `tag_id`. 해당 메일의 부착만 변경. |

성공은 `200`과 변경 여부를 반환하고 확장은 서버에서 현재 태그를 다시 조회한다. 이미 붙은 태그 부착과 이미 해제된 부착의 해제는 같은 대상을 확인한 후 성공 no-op으로 제안한다. 없는 메일이나 부착하려는 태그 정의는 404, 다중 SN 후보나 확인 이후 달라진 대상은 409, 잘못된 요청은 422, 기능 비활성은 503. 인증·권한 실패는 401/403으로 구분한다. `folder_sn`은 기존 조회에서 선택적이며 중복 해소에 사용하지 않는다. 새 변경 계약에도 folder 값으로 대상을 선택하는 동작은 두지 않는다.

서버는 정해진 namespace의 SN 후보가 정확히 하나인 경우에만 내부 메일을 결정한다. 현재 SN 인덱스는 유일하지 않다. 행 잠금만으로 같은 SN의 신규 행 삽입까지 막을 수 없으므로, 수집과 경합할 때도 판정이 유효하도록 DB 트랜잭션·잠금 전략을 격리 PostgreSQL에서 검증한다. 조회 후 유일 후보 자체가 바뀌는 상황도 검토한다. 필요하면 조회에서 서버 발급 단기 불투명 대상 확인값을 사용해 편집 시점에 같은 레코드와 세션인지 다시 대조한다. 이 값은 네이버 계정 일치 증명을 대신하지 않는다.

기존 태그 서비스가 이름 정규화, 동시 생성 시 재사용, 중복 부착 보호 및 해제를 제공한다. 검색은 정규화 이름을 사용하고 최근 태그는 마지막 부착 시각에 따른 공용 추천이다. PostgreSQL에서는 마지막 부착 해제 시 고아 태그 정의가 정리될 수 있으므로 오래된 추천 ID를 다시 선택할 때의 404·재조회 흐름을 검증한다. 태그 기능 자체는 기존 테이블로 가능하다. 해제 후에도 남는 감사 기록은 기존 감사 저장소의 재사용 가능성을 검토한다. 직원, 동작, 결과, 내부 대상 참조와 요청 상관 ID를 제한된 서버 감사에 남기고, 성공 변경의 감사와 태그 쓰기는 같은 트랜잭션으로 커밋한다.

현재 미들웨어는 조회 경로 하나만 다루며, 기존 조회는 Origin이 없는 요청을 헤더·JSON·직원 세션 검사로 처리할 수 있다. 쓰기에는 경로별 허용 메서드·고정 확장 origin·헤더·JSON·크기/빈도 제한을 적용한다. Origin 누락 또는 불일치는 쓰기에서 거부하는 안을 기준으로 실제 MV3 Worker의 요청·preflight를 확인한다. 브라우저 동작이 이 계약을 충족하지 못하면 같은 보호 수준의 세션 결합 CSRF 설계를 확정하기 전까지 활성화하지 않는다. 기존 조회 grant로 쓰기를 허용하지 않는다. 오류와 로그에서 본문·세션·원본 입력을 제거한다.

## 검증과 착수 조건

- **실행 완료** — Overlay `npm test` 38개 통과. 임시 합성 Chromium UI PoC 통과. 이번 문서 작업에서 전체 E2E·실제 ESSMT 쓰기·실제 네이버 상세 검증은 실행하지 않았다.
- **Phase 0 실환경 보완** — 승인된 테스트 프로필에서 이미 읽은 합성 테스트 메일만 사용한다. 받은메일함과 전체메일에서 제목 클릭과 팝업을 구분하여 탭·frame·문서 변화, URL 형식, 상세 SN과 출발 행의 일치 여부를 비교한다. 다음/이전, 닫기, 뒤로가기, 새로고침, 직접 열기와 여러 상세에서 문서·루트·표시 이름의 수명과 삽입 후보를 확인한다. 숫자·문자열 원문 대신 경로 템플릿·건수·일치 여부만 기록한다.
- **Phase 1** — 상세의 단일 메시지 식별을 먼저 입증한다. 별도 쓰기 grant, MV3 Origin/CSRF 계약, SN 중복·대상 변경 시 트랜잭션 정책, 감사 방식과 최근 추천 범위를 확정한 뒤 격리 HTTPS/PostgreSQL에서 신규 API를 시험한다. 0/1/다중 매칭, 동시 수집과 수정, 중복 요청, 오래된 태그, 권한 철회·만료, malformed JSON, Origin/CSRF 및 감사 롤백을 포함한다.
- **Phase 2** — 검증된 상세 진입 방식으로 범위를 좁히고 계정·데이터셋 확인 방식과 표시 위치를 확정한다. 실제 MV3와 합성 DOM·격리 서버에서 여러 탭, 계정·문서·메일 전환, 늦은 응답, 네트워크 장애, 키보드와 기존 Mock·ESSMT 목록 회귀를 시험한다. 운영 적용 전 별도 승인으로 제한된 실환경 검증을 수행하고 상세 수정 후 목록 재조회 정책을 확인한다.
