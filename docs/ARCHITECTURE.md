# 제안 아키텍처 (아직 구현·최종 승인 전)

## 1. 구성요소와 데이터 흐름

```text
네이버 웹메일 (로그인된 브라우저 탭)
  └─ MV3 Content Script
       ├─ SPA 화면 전환/메일 목록 갱신 감시
       ├─ 메일별 mailSN 추출 (방법 검증 필요)
       ├─ 배경 워커에게 일괄 조회 메시지 전달
       └─ 응답된 태그를 배지로 덧그림 (실패 시 원본 UI 유지)
            │
            ▼
      MV3 Extension Service Worker
       ├─ 호출 중복 제거·짧은 메모리 캐시·배치
       ├─ 직원별 ESSMT 인증 상태 확인
       └─ HTTPS API 호출 (최소 권한)
            │
            ▼
      ESSMT 서버의 신규 read-only lookup API
       ├─ 인증/인가/요청량 제한/감사 로그
       ├─ 입력 mailSN 정규화·개수 제한
       ├─ 중복/NULL 관련 정책 적용
       └─ 기존 태그 서비스 활용
            │
            ▼
        emails ↔ email_tag_assignments ↔ email_tags
```

기존 메일 인입 프로세스와 별도이며 **신규 확장은 EML 수집을 수행하지 않습니다.** Content Script가 웹메일 화면의 기존 기능을 방해하지 않도록 실패 시 조용히 기능만 비활성화합니다.

## 2. 식별자/중복 설계

- 1순위는 `naver_mail_sn`으로 개별 메일을 식별. `naver_folder_sn` 또는 메일함 컨텍스트도 함께 전달할 수 있게 인터페이스를 열어 둡니다.
- `naver_thread_id`는 1:N 관계일 수 있으므로 **개별 메일 조회의 단독 키로 사용하지 않습니다.**
- ESSMT에서 `naver_mail_sn`으로 조회된 행이 0건이면 `unmatched`를 반환하고 빈 태그로 오인하지 않습니다.
- 여러 ESSMT 행이 매칭되는 경우를 API 응답에 명시합니다. 태그 병합/우선 선택은 실데이터를 보고 결정합니다.
- `naver_mail_sn`이 NULL인 구형 행을 제목·발신자·시각만으로 자동 확정 매칭하는 것은 1차 버전에서 제외합니다.
- 가능하면 계정/공급자 네임스페이스를 키에 포함해야 합니다. 현재는 네이버 공유 계정 하나이지만 향후 다계정 확장을 고려해야 합니다.

## 3. API 제안 (미구현)

### 입력

`POST /api/browser-overlay/email-tags/lookup` (가칭)

```json
{
  "provider": "naver-mail",
  "messages": [
    {"mail_sn": 12345, "folder_sn": -1},
    {"mail_sn": 12346, "folder_sn": 0}
  ]
}
```

### 출력

```json
{
  "results": [
    {
      "mail_sn": 12345,
      "status": "matched",
      "email_id": 1001,
      "tags": [{"id": 2, "name": "견적요청"}]
    },
    {
      "mail_sn": 12346,
      "status": "unmatched",
      "email_id": null,
      "tags": []
    }
  ]
}
```

위 숫자는 **설계 예시**로 실제 메일 데이터가 아닙니다. `status`에는 `ambiguous` 등의 반환도 고려하며, API 계약은 중복 정책 확정 후 구체화합니다. 공개 문서에 고정된 운영 서버 URL은 넣지 않습니다.

## 4. 인증과 권한 경계

- **공유 네이버 메일 로그인 ≠ ESSMT 사용자 인증.** 여러 직원이 동일 네이버 계정으로 메일을 열더라도 ESSMT API 접근 권한은 각 직원에게 개별 부여합니다.
- 수집용 `X-Ingest-Token`, DB 자격증명, 네이버 쿠키를 새 확장에 배포하지 않습니다.
- 브라우저는 네이버 웹페이지와 ESSMT 서버 사이의 서로 다른 Origin을 사용합니다. 직접 fetch의 CORS, 쿠키 SameSite, CSRF 위험을 검토하고 필요하다면 확장 백그라운드 워커에서 통신합니다.
- 확장 설치 파일에 장기 비밀값 하드코딩 금지. 세션 토큰 저장이 필요하면 만료·폐기·장치 분실 대응 정책을 먼저 확정.
- 권한은 필요한 호스트에만 제한하며, 최초 릴리스에서는 메일 본문/첨부를 서버로 재전송하지 않습니다.
- 로그·진단 데이터에서 메일 제목·발신자·본문·쿠키·토큰을 제외하거나 마스킹합니다.
- 엔드포인트에는 요청 개수 제한, 사용자 인증/인가 및 간단한 감사 로그를 둡니다.

## 5. 확장 UI와 성능

- 목록 각 행에 해시태그 chip을 삽입하고 메일 상세 화면 상단에도 표시하는 것을 제안합니다. 네이버 기본 UI의 버튼·읽음/미읽음 동작을 건드리지 않습니다.
- SPA 전환과 가상 스크롤을 고려하여 DOM 변경 감시, 배지 중복 삽입 방지, 화면 이탈 시 조회 취소를 설계합니다.
- 목록 한 화면에 메일 30~100건이 보여도 한 건마다 요청하지 않고 batch lookup을 사용합니다.
- 조회 실패·로그아웃·권한 없음·미수집은 각각 별도 상태로 표현할 수 있도록 내부 상태를 분리합니다.
- 태그를 단순히 렌더링하는 PoC에서는 쓰기 권한을 부여하지 않습니다.

## 6. 공개 저장소 보안·라이선스 메모

- 공개 레포에는 실제 메일·고객 데이터·내부 인입 토큰·운영 사용자명·브라우저 프로필 경로를 넣지 않습니다.
- 기존 ESSMT 비공개 코드 전체 또는 수집 확장 코드의 무단 전재는 필요하지 않습니다. 데이터 계약과 조사 사실을 자체 문서로 기술합니다.
- 향후 코드가 추가되면 `.env*`, 브라우저 프로필, 키, 로컬 옵션 덤프, 네트워크 캡처를 `.gitignore`로 제외해야 합니다.
- 라이선스는 아직 결정되지 않았습니다. 공개 저장소라는 사실만으로 오픈소스 라이선스가 부여되는 것은 아닙니다.
